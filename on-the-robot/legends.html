Changing legends in a match#

A screen key can show a different legend as the match goes on — INTAKE while you are collecting, SCORE while you are lined up, CLIMB in the endgame. This page is how the robot tells it to.

It is the one place the Button Board asks for code on the robot. Everything else about the board is an ordinary gamepad.

This describes the design, not something you can plug in today. The screenkey1 tile has never been manufactured, and it has not been established that the FTC Driver Station forwards a rumble call to this board at all. The library is written, tested against both ends of the arithmetic, and unproven on hardware. Read What is not proven before you rely on it in a real match.

Why rumble, of all things#

For FTC the board presents itself as an Xbox-style gamepad, and that leaves it with exactly one interface — no serial port, no config channel. During a match there is no way in.

Except one. The Driver Station can send a gamepad a rumble command, and gamepad.rumble() is a normal thing for an OpMode to call. That is a very narrow door: it carries a number, not text. But a stored picture is switched by a number, so the number is all we need.

The trade is: load the legends before the match, switch them during it with one call.

The number is a legend code, not a key#

showLegend(3) does not mean “key 3”. It means “whatever the config app has bound to code 3” — see Binding legend codes.

Name the codes in your OpMode for what they mean, and the numbers appear in exactly one place:

static final int LEGEND_INTAKE = 1;
static final int LEGEND_SCORE  = 2;
static final int LEGEND_CLIMB  = 3;

Someone can then rearrange the panel — a different key, a different picture — without anyone touching the robot code.

Adding the library#

FTC teams copy files; there is no dependency to add beyond the SDK you already have. From the repository:

cp -r robot/ftc/src/org      TeamCode/src/main/java/
cp -r robot/ftc/src-ftc/org  TeamCode/src/main/java/

That leaves three files in org/firstinspires/ftc/teamcode/buttonboard/. Do not copy test/ — it is for a desktop JDK and Android Studio will try to build it. If your team uses a different package root, change the package line in all three files to match.

The rumble API landed in FTC SDK v7.0; nothing here needs anything newer.

A minimal OpMode#

@TeleOp(name = "Button Board legends")
public class LegendDemo extends LinearOpMode {

    static final int LEGEND_INTAKE = 1;
    static final int LEGEND_SCORE  = 2;
    static final int LEGEND_CLIMB  = 3;

    @Override
    public void runOpMode() {
        // gamepad1 must be the pad the Button Board bound as.
        ButtonBoard board = new ButtonBoard(new GamepadRumbleSink(gamepad1));

        waitForStart();

        while (opModeIsActive()) {
            // Safe to call every loop: it sends only when the code changes.
            if (gamepad1.right_trigger > 0.5) {
                board.showLegend(LEGEND_CLIMB);
            } else if (gamepad1.a) {
                board.showLegend(LEGEND_SCORE);
            } else {
                board.showLegend(LEGEND_INTAKE);
            }

            telemetry.addData("legend", board.lastLegend());
            telemetry.update();
        }
    }
}

The config app writes this call out for you: the Legend codes section has an In the OpMode block with the exact line for every code you have bound, and a Copy button.

The API#

Call Does
showLegend(int code) Show the legend bound to code — unless it is already the last one sent. Returns whether it sent anything. Throws on anything outside 1–15.
refresh() Send the last code again regardless. For when the board was power-cycled and your belief about it is stale.
forget() Drop that belief without sending. The next showLegend sends whatever it is given.
lastLegend() The last code sent — not what the board is known to be showing.
stopRumble() Send zero power. Stops a real gamepad buzzing; does not clear the key.

Call it every loop#

showLegend() remembers what it last sent and suppresses repeats, which is the entire reason to use it rather than calling rumble() yourself. An OpMode loop runs at about 50 Hz, and the SDK’s own sample is blunt about not spamming the rumble motors.

So write it as a plain statement of what the legend should be right now, and let it work out whether anything needs sending.

There is no way to blank a key#

Zero is the SDK’s stop, so the board ignores it — deliberately, because ending a rumble must not wipe a screen. To show nothing, store a blank picture in a slot, bind a code to it, and show that code.

If the board is unplugged mid-match#

Nothing tells you. There is no acknowledgement on this path at all: a board in FTC mode cannot answer.

If it is power-cycled it comes back showing whatever its map starts with, while your OpMode still believes the legend it last sent — so the next showLegend() of that same code is suppressed as a repeat and the panel stays wrong. refresh() is the way out, wired to a button you can reach.

Do not use it as an animation#

The SDK keeps one outgoing rumble at a time and sends it about every 50 ms. Two calls inside one of those windows means the first is thrown away, not queued.

That is harmless here, because a code names a legend absolutely — the panel converges on the latest one you asked for. What it costs is intermediate legends: flick A → B → C inside 50 ms and B may never appear. If a legend needs to be seen, leave it up for at least a tenth of a second.

Rumble goes to one gamepad. Whichever position the Driver Station gave the board — gamepad1 or gamepad2 — is the one to construct GamepadRumbleSink with. Send to the other and nothing happens, with no error.

Setting the board up first#

The codes mean nothing until the pictures are on the tile and the codes are bound, and neither can be done in FTC mode — that is the whole reason this channel exists. The order is:

  1. Put the board in a mode that has the config channel: frc in the config app’s Connect screen. Save, then unplug and plug back in.
  2. Load the pictures into slots and bind the codes. Save.
  3. Switch back to xinput, save, unplug and plug back in.
  4. Check which gamepad position the Driver Station gives it.

The bindings live in your saved configuration, so step 2 survives step 3.

The config app offers a “bind the next code” button that waits for a rumble and binds whichever code arrives. Against a real board it will wait forever. No single board can both receive a rumble and report that it did — the mode with the rumble endpoint has no config channel to report on. It works against the fake board, and it becomes real if the two are ever combined. Bind by picking the number instead; that works everywhere.

What is not proven#

None of this has run on hardware, and it is worth being precise about which parts are assumptions:

  • No part of this path has been tested on a real board — not the OpMode, not the Driver Station’s forwarding, not the board’s decoding of a real rumble packet.
  • That the Driver Station forwards a rumble to this board is not established. What has been tested is only that an FTC Driver Hub recognises the board as a gamepad. Whether its rumble path reaches a device with this board’s identity is exactly the open question.
  • The ~50 ms rate limit is read out of the SDK’s source, not measured.
  • Latency is unknown. Showing a stored picture takes about a frame at the tile, but the time from showLegend() to pixels also includes the Driver Station, the radio link and the bus, and none of it has been timed.
  • isRumbling() will say true for the length of each step even though the board has no motors to rumble. Do not gate legend changes on it — you would suppress real ones.
